## 2. Taxonomy (`data/phishing_taxonomy.json`, `phishgate/intake/taxonomy.py`)

The three labels in `schemas/verdict.py` stay as they are. The taxonomy is the indicator
catalogue behind them: what has to be found in a mail for it to fall under one of the three.

* **The file** has eight categories (legitimate, commercial spam, credential phishing, spear
  phishing, BEC, malware delivery, advance-fee scam, callback). Each now carries the verdict
  label it maps to (`legitimate` and `commercial_spam` are benign, the six others phishing)
  and the reason codes the model should cite, all from the existing `ReasonCode` list.
* **Suspicious comes from rules, not from a category.** Three `label_rules` say when a mail is
  phishing (theme plus the payload or request the category needs), suspicious (the theme
  without the payload, or a hard or soft indicator without a category, or contradictory
  evidence) and benign (legitimate or spam, and no indicator at all).
* **Tie-break rules** are in precedence order (first match wins), which the original file did
  not say; a targeted mail with a macro attachment is spear phishing, not malware delivery.
  A sixth rule separates BEC from callback lures. `none` is gone from the multi-label
  `vector` tag.
* **The prompt** is built from the file: `prompt_section()` renders categories, indicators,
  label rules and tie-breaks as fixed text after the system instructions, outside the data
  block. The system prompt grows from about 800 to about 6,000 characters.
  `PHISHGATE_TAXONOMY=0` leaves it out, for the ablation run.
* **`load_taxonomy()` validates the file** on first use: unique ids, every label one of the
  three, every reason code in the schema, one rule per label. A broken file is an error at
  import time, never a silent gap in the prompt.
* **What it does not do.** The content indicators (generic salutation, secrecy framing, phone
  number as the only call to action) are judged by the model only. The verifier still checks
  the computed facts and nothing else. The taxonomy raises what the model looks for; it adds
  no guarantee. That is the accepted residual risk of layer 3.

## 4. Approver-fatigue test (`scripts/approver_fatigue.py`, `tests/test_approval.py`, plan item S-7)

Layer 5's residual risk is an analyst who approves everything. The proposal measures it
with planted bad drafts.

* `plant` queues honest drafts and bad ones in a shuffled order, straight into the queue,
  bypassing the gate on purpose (the question is whether the human notices). The five bad
  kinds are what the gate must never produce: attacker text appended, a link in the body, a
  changed subject, a template that is not allow-listed, a blank field. The answer key is
  written outside the workspace.
* `score` compares the analyst's decisions with the key: `bad_approved_rate` is the number
  to report.
* `draft_problems()` checks a queued draft against its template with gate-shaped values
  for the placeholders. Every planted bad draft fails it, a draft the real gate produced
  passes. The analyst page could show it next to each draft (that is `web.py`, Junhee's).
* `test_approval.py` also pins the approval rules themselves: every message waits for a
  click and a reject leaves nothing in `outbox/`; a bulk quarantine over 5 waits and a
  smaller one runs; the 10-messages-per-hour limit refuses the eleventh. The hourly limit
  had no test before.
